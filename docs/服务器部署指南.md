# 服务器部署指南：从零到跑通第一个真任务

这份指南假设两件事：**你本地是 Windows**，**你从没用过服务器**。
所以每条命令都可以直接复制，每个坑都标了"报错长什么样"。

一句话版本：本地先把不需要 GPU 的活干完（能覆盖约 70% 的工作量），
服务器上只做 5 件事——**体检、装环境、传数据、起模型、跑批**。

本页以当前可运行的 BM25 与生成链路为部署示例。正式实验包含向量和混合检索、重排序、重检索、重新生成及拒答，按[实验排期](02_学习与实验计划_按周排期.md)实施。

---

## 0. 整体流程

```
本地（Windows）                        服务器（Linux + GPU）
─────────────────                     ──────────────────────
① 装 Python 环境                       ① ssh 进去，跑 onboarding_server.sh 体检
② 下载 CRAG 数据                       ② 建 conda 环境，装 torch / vllm
③ 规整 + 切分 + 切块（CPU）            ③ 传代码和数据（rsync）
④ 建 BM25 索引（CPU，秒级）            ④ 下模型权重（HF 镜像）
⑤ 拼 prompt，用 mock 跑通解析          ⑤ 起 vLLM 服务（tmux 里）
⑥ 指标 + 画图代码跑通（合成数据）      ⑥ 冒烟测试 → 跑 50 题 → 跑全量
⑦ 建 git 仓库，练一次 rsync            ⑦ 结果落在 results/runs/，rsync 拉回
```

判断标准很简单：**凡是"能在一台没有显卡的电脑上跑完"的步骤，都放在本地做完再传。**
服务器按小时计费或在共享队列里排队，把 CPU 活搬到上面做是纯浪费。

## 1. 本地现在就能做的 8 件事

按这个顺序做，一天能做完前 5 件。

### 1.1 装本地环境（20 分钟）

```powershell
cd E:\26年\毕设\实验
python -m venv .venv
.\.venv\Scripts\Activate.ps1        # 如果报"禁止运行脚本"，见下面这行
# Set-ExecutionPolicy -Scope CurrentUser RemoteSigned

pip install -r requirements.txt
pip install pytest                   # 可选，用来跑单元测试
python scripts\00_check_env.py
```

`00_check_env.py` 会打印：Python 版本、每个包装没装、有没有 GPU、磁盘剩余、配置能否加载。
**它最后一行是结论。** 缺核心包它会告诉你装哪个。

预期结果：`结论：核心环境 OK。` + `无 GPU —— 仍可完成：数据准备、BM25 建索引、prompt 联调、指标与画图。`
这条"无 GPU"提示不是安慰，是本指南第 11 节的降级路径。

> **本机实测（2026-11-02）**：你这台机器有 `RTX 4060 Laptop GPU, 8188 MiB, 驱动 566.43`，
> E 盘剩余 238.8 GiB。8 GB 显存意味着两件事：
> ① 装好 torch 后 `00_check_env.py` 会打印 `torch.cuda : True`，不用等服务器就能验证"真模型"；
> ② 显存够跑 **3B bf16**（约 6.4 GB）或 **7B-AWQ 单流**（4.4 GB 权重 + 少量 KV），
> 但**不够**跑 7B bf16，也不够开并发——所以"调 prompt、看生成质量"可以本地做，
> 正式对照的批量推理安排在服务器上。
> 这是最省服务器排队时间的组合：本地把 prompt 调对，服务器上只做批量搬运。

### 1.5 不用 GPU 跑通"检索→prompt→解析"（30 分钟）

把配置里的后端改成 mock（不调模型，返回固定结构）：

## 2. 服务器到手第一小时：先体检，别急着装东西

### 2.1 连上去

```bash
ssh 用户名@服务器IP -p 端口        # 端口默认 22，很多学校不是
```

第一次会问 `yes/no`，输入 `yes`。以后建议配密钥免密：

```powershell
# 本地执行一次
ssh-keygen -t ed25519
type $env:USERPROFILE\.ssh\id_ed25519.pub | ssh 用户名@服务器IP "mkdir -p ~/.ssh && cat >> ~/.ssh/authorized_keys"
```

### 2.2 上传项目并体检

```bash
# 服务器上
mkdir -p ~/mvs && cd ~/mvs
# （本地已经 rsync 过代码，这里假设 src/ scripts/ configs/ 已在）
bash scripts/onboarding_server.sh
```

它会检查 5 组东西并给出结论：GPU 与空闲显存、Python 版本、关键包、HF 镜像连通性、是否在项目根。

**最重要的两行**：

```bash
nvidia-smi
```

看两件事：`Memory-Used` 是不是接近 0（共享卡上如果别人占着，你起服务会 OOM），
`Driver Version` 是多少（决定能装哪个 CUDA 版本的 torch）。

**共享服务器上动手前先看一眼显存**，这是最基本的礼貌，也能省你半小时排查。

## 3. 装环境（三选一，建议 A）

### 3.1 方案 A：conda（最稳，推荐新手）

```bash
# 1) 装 miniconda（如果没有）
wget https://repo.anaconda.com/miniconda/Miniconda3-latest-Linux-x86_64.sh
bash Miniconda3-latest-Linux-x86_64.sh -b -p ~/miniconda3
~/miniconda3/bin/conda init bash && source ~/.bashrc

# 2) 建环境（3.10 或 3.11，别用 3.12：部分 vLLM 版本还没跟上）
conda create -n mvs python=3.10 -y
conda activate mvs

# 3) 装 torch（cu121 对应驱动 >= 525；用 nvidia-smi 右上角的 CUDA Version 判断）
pip install torch --index-url https://download.pytorch.org/whl/cu121

# 4) 装项目依赖
pip install -r requirements.txt
pip install -r requirements-server.txt

# 5) 把项目装成可导入的包
pip install -e .

# 6) 验证
python -c "import torch; print(torch.__version__, torch.cuda.is_available())"
```

`torch.cuda.is_available()` 必须是 `True`。是 `False` 的话，常见原因：驱动太旧、装成了 CPU 版 torch。

### 3.2 方案 B：uv（快，适合已经熟的人）

```bash
curl -LsSf https://astral.sh/uv/install.sh | sh
uv venv --python 3.10 .venv
source .venv/bin/activate
uv pip install torch --index-url https://download.pytorch.org/whl/cu121
uv pip install -r requirements.txt -r requirements-server.txt
uv pip install -e .
```

### 3.3 装 vLLM（单独一步，最容易出错）

vLLM 对 torch 版本极其敏感，**不要写进 requirements.txt 一次性装**：

```bash
pip install vllm                      # 让它自己挑匹配的 torch
# 或指定版本（查 https://pypi.org/project/vllm/ 看与 CUDA 的对应表）
pip install vllm==0.6.3
```

常见后果：装 vLLM 会把 `torch`、`transformers` 的版本改掉。
**这是正常的**，但装完必须立刻验证，而不是等到跑实验才发现：

```bash
python -c "import torch, vllm; print('torch', torch.__version__, torch.cuda.is_available()); print('vllm', vllm.__version__)"
python scripts/09_smoke_vllm.py --base-url http://127.0.0.1:8000/v1   # 服务起来后才跑
```

如果 vLLM 死活装不上（编译报错、版本冲突），**果断放弃 vLLM**，用方案 C 或第 11 节的 API 兜底。
若换推理后端，实验台账应记录后端、模型版本及延迟测量条件。

### 3.4 方案 C：transformers 直接推理（备选，慢但简单）

不装 vLLM，用 `transformers` + `accelerate` 加载模型。吞吐大约低 3—5 倍，
但你的全量生成在 4090 上也只要 3—5 小时（vLLM 是 0.6—0.9 小时），
**如果 vLLM 卡住了，这个兜底方案完全能接受**。

## 4. 把代码和数据传上去

### 4.1 传代码（每次改动后）

```powershell
# 本地，Git Bash 或装了 rsync 的 PowerShell
rsync -avz --delete `
  --exclude '.venv' --exclude '__pycache__' --exclude 'data' `
  --exclude 'logs' --exclude 'results' --exclude '.git' `
  -e "ssh -p 22" `
  E:/26年/毕设/实验/ user@server:~/mvs/
```

`--delete` 会让远端和本地一致（本地删掉的文件远端也删）。
第一次用建议先加 `--dry-run` 看它打算做什么。

如果服务器能连 GitHub，更省事：`git clone` 之后 `git pull` 更新。

### 4.2 传数据（只传一次）

```powershell
# 原始数据（几十 MB 到几百 MB）
rsync -avz E:/26年/毕设/实验/data/raw/ user@server:~/mvs/data/raw/

# 规整好的题目和切块（可选：服务器上重跑 01 脚本也能生成，但传更快）
rsync -avz E:/26年/毕设/实验/data/processed/ user@server:~/mvs/data/processed/
rsync -avz E:/26年/毕设/实验/data/interim/ user@server:~/mvs/data/interim/
```

**不要传** `data/index/*.pkl`：服务器上重跑 `02_build_index.py` 只要几秒，
而且 pickle 文件跨 Python 版本可能读不了。

**不要传** `.venv/`：里面的路径全是 Windows 的，传上去必然报错。

### 4.3 断点续传（大文件用）

```bash
rsync -avz --partial --progress data/raw/ user@server:~/mvs/data/raw/
```

`--partial` 会在中断后从断点继续，而不是重来。

## 5. 下模型权重

### 5.1 走镜像（国内服务器必做）

```bash
export HF_ENDPOINT=https://hf-mirror.com
export HF_HOME=~/mvs/.cache/huggingface     # 指到数据盘，别放系统盘
mkdir -p "$HF_HOME"

pip install -U "huggingface_hub[cli]"
hf download Qwen/Qwen2.5-7B-Instruct --local-dir ~/mvs/models/qwen2.5-7b-instruct
```

7B 的 bf16 权重约 **15 GB**。下之前先 `df -h` 看磁盘。

**把这两个 `export` 写进 `~/.bashrc`**，否则新开的 tmux 窗口里又连不上了：

```bash
echo 'export HF_ENDPOINT=https://hf-mirror.com' >> ~/.bashrc
echo 'export HF_HOME=~/mvs/.cache/huggingface' >> ~/.bashrc
```

### 5.2 服务器完全没网怎么办

在本地下好，打包传上去：

```powershell
hf download Qwen/Qwen2.5-7B-Instruct --local-dir D:\models\qwen2.5-7b
# 打包（-1 表示不压缩，权重本来就压缩过了，压不动）
tar -cf qwen.tar -C D:\models qwen2.5-7b
scp qwen.tar user@server:~/mvs/models/
```

服务器上 `tar -xf qwen.tar`，然后在启动 vLLM 时用 `--model ~/mvs/models/qwen2.5-7b`。

### 5.3 显存紧张时选量化版

| 模型 | bf16 权重 | INT4(AWQ) | 24GB 卡上 bf16 并发 | AWQ 并发 |
|---|---|---|---|---|
| Qwen2.5-7B | 15.2 GB | 4.4 GB | 约 22 | 约 68 |
| Llama-3.1-8B | 16.1 GB | 4.7 GB | 约 8 | 约 28 |

需要更高并发或显存被占时，换 `Qwen2.5-7B-Instruct-AWQ` + 启动参数 `--quantization awq`。

## 6. 起 vLLM 服务

### 6.1 一定要在 tmux 里跑

```bash
tmux new -s vllm          # 新建会话
cd ~/mvs
bash scripts/serve_vllm.sh
# 看到 "Uvicorn running on http://127.0.0.1:8000" 就是起来了
# Ctrl+B 然后按 D         → 脱离会话，服务继续跑
# tmux a -t vllm          → 回来看日志
```

**不要**直接 `python ... &`：ssh 一断，进程可能被 SIGHUP 杀掉，
而且你再也看不到日志。

### 6.2 三个参数决定成败

| 参数 | 建议值 | 为什么 |
|---|---|---|
| `--gpu-memory-utilization` | 0.88 | 24GB 卡留 12% 给 CUDA context 和碎片；设 0.95 经常在长 prompt 时 OOM |
| `--max-model-len` | 4096 | 你的 prompt 是 5 页 ≈ 3000 token + 输出 256；设太大白吃显存 |
| `--max-num-seqs` | 8—16 | 并发数。共享卡上别贪心，显存是按最坏情况预留的 |

### 6.3 验证服务

```bash
# 另一个 tmux 窗口或另开 ssh
curl http://127.0.0.1:8000/v1/models
python scripts/09_smoke_vllm.py --base-url http://127.0.0.1:8000/v1
```

`09_smoke_vllm.py` 会依次检查：端口通不通、能不能生成、中文有没有乱码、延迟多少。
**这三行输出截图存下来**，写论文"实验环境"一节时直接引用。

### 6.4 如果你的电脑要连服务器上的服务

vLLM 默认只监听 `127.0.0.1`（正确且安全）。本地想调，用 ssh 隧道：

```powershell
ssh -L 8000:127.0.0.1:8000 用户名@服务器IP -N
# 然后本地就能访问 http://127.0.0.1:8000/v1
```

**不要**把 vLLM 绑到 `0.0.0.0` 且不加认证——那等于把一张显卡挂在公网上。

## 7. 跑第一个真任务（顺序别跳）

```bash
# ① 只跑 5 题，确认端到端能通
python scripts/03_generate.py --config configs/exp/e0_smoke.yaml --limit 5

# ② 检查产物
ls -lh results/runs/E01_*/
head -1 results/runs/E01_*/gen.jsonl | python -m json.tool
cat results/runs/E01_*/stats.json

# ③ 看两个数
#    parse_ok 为 true 的比例（应该 > 95%）
#    sec_per_question（用实际题数估算批量生成时间）
```

`stats.json` 里的 `sec_per_question` 是关键：**先算时间再决定要不要跑全量**。
用实际评测题数乘以试跑的平均耗时估算批量生成时间。完整方法还需计入重排序、验证与重试。

### 7.1 全量跑

```bash
# 后台跑，日志落盘
bash scripts/run_bg.sh gen_full python scripts/03_generate.py --split all

# 跟踪
tail -f logs/gen_full_*.log
```

此命令遍历当前处理产物的所有划分。正式比较使用官方公开测试集，并按已冻结的配置单独运行。

因为 `03_generate.py` 每条结果都 `append_jsonl` 并 flush，
**中途断了直接重跑同一条命令**，它会自动跳过已完成的题（`done_keys`）。

### 7.2 分片跑（多人共用一张卡时）

```bash
# 开 3 个 tmux 窗口，各跑一段
python scripts/03_generate.py --split all --limit 1500
```

更干净的做法是加 `--shard 0/3` 这类参数（当前未实现，需要时加 10 行代码），
但注意：**多个进程同时写同一个 gen.jsonl 会互相覆盖**，必须各写各的文件。

## 8. 收工与取回结果

### 8.1 每天的收工三件事

```bash

tail -3 logs/gen_full_*.log

# 2) 确认磁盘没满（最容易忽略，满了会静默写坏文件）

# 3) 把当天的结果拉回本地（防服务器被回收/清盘）
```

**第 3 条是保命的。** 学校服务器重置、磁盘配额清理、实例到期，
这些事在毕设期间都真实发生过。别把四个月的实验结果只留在一个地方。

```bash

```

只把 `results/figures/*.png` 和 `results/tables/*.csv` 拉回来。

## 9. 常见报错：看到这条就查这张表

| 报错 | 原因 | 解决 |
|---|---|---|
| `CUDA out of memory` | `gpu-memory-utilization` 太高 / 并发太大 | 降到 0.85，`--max-num-seqs 4`，加 `--enforce-eager`，或换 AWQ 模型 |
| `torch.cuda.is_available() == False` | 装了 CPU 版 torch / 驱动太旧 | `pip install torch --index-url .../cu121`，`nvidia-smi` 确认驱动 |
| `undefined symbol: ...` | torch 与 vllm 版本不匹配 | 卸掉重装：`pip uninstall vllm torch -y` 后按 §3.3 顺序装 |
| `Connection refused` 连 8000 | 服务没起 / 端口不对 / 监听 127.0.0.1 | `ss -ltnp` 查 8000 端口，再确认服务日志里 Uvicorn 已启动 |
| 下载模型卡在 0% | 没设 `HF_ENDPOINT` | `export HF_ENDPOINT=https://hf-mirror.com`（写进 `.bashrc`） |
| `Permission denied (publickey)` | 密钥没配好 | 重跑 `ssh-copy-id`，或检查 `~/.ssh` 权限 700 |
| `No space left on device` | 磁盘满 | 按体积排序看 `du -sh ~/mvs/*`，清 `logs/`、旧 `results/runs/` |
| `bash: $'\r': command not found` | Windows 换行符（CRLF） | `sed -i 's/\r$//' scripts/*.sh`，或 `git config core.autocrlf input` 后重新 checkout |
| 跑到一半 ssh 断了进程没了 | 没用 tmux/nohup | 重跑即可（有断点续跑）；以后一律 `tmux` |
| `Killed`（无 Python 报错） | 被系统 OOM killer 杀了（内存，不是显存） | 减小 batch；用 `dmesg` 看末尾确认；百万级 BM25 换 `bm25s` |

## 10. 如果你是"共享卡"用户：四条规矩

1. **起服务前先 `nvidia-smi`**，`Memory-Used` 不是 0 就别起，先问是谁在用；
2. **`--gpu-memory-utilization` 别超过 0.85**，把余量留给别人和碎片；
3. **跑完立刻 `Ctrl+C` 或 kill**，别让服务挂一晚上占着卡；
4. **长任务放 tmux**，别在前台跑——别人登录看到你的进程在前台，会被管理员提醒。

## 11. 万一一直拿不到卡：三条降级路径

按推荐顺序：

**路径 A：云端 API（最省事）**
把 `configs/model/qwen25_7b.yaml` 的 `backend` 改成 `openai`，
填 `base_url` / `api_key`（任何 OpenAI 兼容服务都行）。
用试跑的实际 token 数和额外调用比例估算成本。API 延迟包含网络和服务排队，单独记录测量环境。

**路径 B：CPU + 小模型（最省钱）**
用 `Qwen2.5-0.5B` 或 `Llama-3.2-1B` 在 CPU 上跑，慢但能出结果。
适合验证管线，不适合报最终指标（生成质量太差，拒答比例会失真）。

**路径 C：缩小开发集的配置搜索**
先缩小开发集的参数搜索规模，保留检索类型、切分、召回数、重排序方法及自适应动作的核心对照。资源允许后再跑换模型和 RGB 补充实验。

## 12. 附录 A：向导师/管理员要机器时该问什么

拿着这张清单去问，一次问清，别来回拉扯：

1. 有没有**共享 GPU 服务器**？卡型号和显存是多少（4090 24G / A100 40G / 其他）？
2. 能不能**独占一张卡**跑几小时，还是只能排队/共享？
3. 有没有**容器环境**（Docker/Singularity）还是直接给 ssh？
4. **能不能连外网**？能不能访问 HuggingFace（或需不需要镜像/代理）？
5. **磁盘配额**多少？模型权重 15 GB + 中间产物，需要留 60—100 GB。
6. 有没有**时长限制**（任务跑超过 N 小时被 kill）？
7. 账号是**长期有效**还是按学期/项目周期？毕设跨到明年 5 月，中途会不会被回收？
8. 出了问题找谁（群/邮箱），响应大概多久？

用试跑吞吐、各阶段题量及实际重试比例估算 GPU 小时，按建索引、主实验和消融实验三个窗口安排。

**把"我什么时候需要卡"说清楚，比空泛地说"我需要 GPU"更容易批下来。**
